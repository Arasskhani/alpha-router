1. Executive summary and scope

The Alpha Router security remediation addressed the principal application, browser, media, outbound-network, sandbox, billing, deployment, and operations risks identified during the audit. The repository contains corresponding controls, regression tests, deployment hardening, and an operations runbook. The work is best described as implemented in the reviewed repository, with deployment-specific acceptance and fleet-wide operational evidence still required.

Scope covered authentication and sessions; authorization and Media IDOR; rate limiting; SSRF; code execution isolation; bounded input/output; image generation reliability and billing; encryption at rest and key migration; browser security; production configuration; Redis; OpenAPI exposure; containers; health and observability; CI/dependency checks; backup/restore and rollback procedures; and final local object-storage credential rotation.

Secret-free record: This report contains no passwords, tokens, API keys, connection strings, secret values, or sensitive user data. Names and categories are used only where needed to describe a control. The omission is intentional.

Outcome at a glance

  • COMPLETED Core security controls and their regression-test coverage are present in the repository.
  • COMPLETED Production guard defaults to fail-closed and checks the major secret, transport, broker, Redis, encryption, and documentation requirements.
  • COMPLETED The sandbox broker is separated from Alpha Router application traffic; Alpha Router no longer needs a Docker socket.
  • DEFERRED Fleet-wide metrics, external secret-management proof, production penetration testing, and long-term CSP enforcement remain deployment work.
  • RESIDUAL Redis fallback is intentionally fail-open for availability; process-local observability counters are not durable audit records; the legacy JWT response remains for compatibility even though browser storage moved to cookies.

2. Methodology and gates

The remediation was reviewed chronologically against the repository’s implementation and test seams. Each phase was evaluated using four gates:

  1. Control gate: the security behavior is implemented with safe defaults and bounded inputs.
  2. Regression gate: focused tests cover both allowed and denied paths, failure modes, and compatibility behavior.
  3. Deployment gate: Compose, startup validation, non-root/container restrictions, TLS/configuration checks, and service health are represented.
  4. Operations gate: signals, runbook actions, backup/restore, rollback, and recovery guidance exist without secrets.

Repository evidence includes the Python backend tests, security services, authentication and media routes, image-generation services, Dockerfiles/Compose, .env.example, and docs/SECURITY_OPERATIONS_RUNBOOK.md. This report does not treat source presence as proof of a completed production rollout.

3. Chronology: Phases 0–10

Phase 0 — Baseline hardening and production guard COMPLETED

Established the baseline security posture and a production startup gate. Development remains compatible with development defaults, while production rejects insecure placeholders and missing critical configuration. The guard covers application/admin/gateway/service-admin categories, database and transport settings, code-subprocess fallback, and later-expanded requirements. It avoids logging secret values and supports an explicitly temporary warning mode, while the default is hard-fail.

Phase 1 — Abuse controls and request bounds COMPLETED

Replaced the effective per-worker-only rate-limit behavior with Redis-backed shared sliding-window checks and a bounded in-process fallback. Login protection applies independent per-username and per-source-IP windows before password verification. Chat list/search paths and related request surfaces received rate-limit coverage. Request/body and media limits were bounded, including streamed broker request bytes, code/file counts, file sizes, result sizes, and image input limits.

Phase 2 — Media authorization and IDOR remediation COMPLETED

Centralized object-level authorization for media assets. A user may access their own asset; cross-user reads require the appropriate media/users role, and cross-user deletion requires users-write authorization. Unauthorized existence is hidden with a not-found response. Image-reference resolution uses the same authorization path, preventing a guessed Media ID from being used as an upstream reference.

Phase 3 — Secrets at rest and bounded I/O COMPLETED

Introduced a single encryption/decryption primitive for provider API keys, SMTP credentials, and directory/identity-provider bind credentials stored in the database. New writes use Fernet derived with PBKDF2-HMAC-SHA256; legacy plaintext/ciphertext compatibility supports incremental migration. Bounded I/O and cleanup protections were added for media, ZIP generation, image decoding, streaming, and subprocess output, reducing memory exhaustion and partial-resource leakage.

Phase 4 — Sandbox broker and subprocess isolation COMPLETED

Separated the sandbox control plane into an authenticated internal broker. The application calls the broker rather than owning the Docker socket. The broker authenticates before body parsing, rejects oversized streamed requests, validates filenames, limits concurrency and queue time, and fails closed when authentication or the runtime is unavailable. Sandbox execution uses no network, read-only root storage, a constrained temporary filesystem, memory/CPU/PID/file limits, an unprivileged user, all capabilities dropped, no-new-privileges, bounded stdout/stderr, execution timeout, and forced cleanup. The insecure direct subprocess fallback is disabled by production policy.

Phase 5 — SSRF and outbound URL hardening COMPLETED

Centralized HTTP(S) URL validation for web fetches, image references, and media imports. Hostnames are resolved and all returned addresses are checked against loopback, private, link-local, multicast, reserved, and unspecified ranges, including cloud metadata ranges. Userinfo and invalid schemes/ports are rejected. A pinned transport dials the validated address, environment proxy trust is disabled, and redirect targets can be revalidated. Private-range access is an explicit opt-out for controlled self-hosted deployments, not the default.

Phase 6 — Identity, session, and URL controls COMPLETED

Added provider-binding protections so OIDC identity subjects are stable and cross-provider username collisions cannot silently take over an existing local or LDAP account. OIDC uses state, nonce, PKCE, issuer/audience/expiry validation, userinfo subject matching, and a one-time exchange code rather than placing the JWT in a redirect URL. Frontend/API/identity-provider URL validation was hardened. Session cookies are HttpOnly with CSRF protection; token-version revocation invalidates logout, disabled-account, and administrative-session changes. Legacy Bearer JWT acceptance remains as a compatibility path and is explicitly recognized as residual risk.

Phase 7 — Budgets, API-key reservations, and login protection COMPLETED

Added atomic budget and Alpha Router API-key credit reservations using row locks, scoped idempotency keys, bounded holds/TTLs, settle/release transitions, and stale-hold expiration. This closes race conditions that could overspend user budgets or API-key credit under concurrent requests. Image generation and chat/embedding operations use reservation and settlement paths. Login brute-force controls were integrated with the shared rate-limit service.

Phase 8 — Browser security headers and staged CSP COMPLETED

Added baseline headers including MIME sniffing protection, frame denial, strict referrer policy, Permissions-Policy, and Cross-Origin-Opener-Policy. CSP is available in Report-Only mode for safe rollout, independently from enforcement. HSTS is conditional on production, HTTPS, and explicit enablement, with conservative max-age and explicit subdomain inclusion. This preserves a measured rollout rather than asserting that CSP is already enforced everywhere.

Phase 9 — Production gate expansion, Redis, OpenAPI, and key rotation COMPLETED

Expanded the production gate to require authenticated Redis, a dedicated data-encryption key, and admin-only OpenAPI documentation. Redis configuration supports password authentication while retaining a documented compatibility path for existing single-box deployments; runtime fallback is observable. OpenAPI/Swagger/Redoc paths return not-found to unauthenticated or non-Super-Admin users when the production flag is enabled. Encryption key migration is multi-key: the primary dedicated data key is tried first, then the legacy key, allowing old rows to remain readable while re-encryption proceeds idempotently.

Container hardening was completed in Compose and related images: Alpha Router and the broker use non-root execution, capability dropping, no-new-privileges, read-only roots, constrained tmpfs mounts, isolated networks, and health checks. The broker alone receives the Docker socket, reflecting the intended trust boundary.

Phase 10 — Health surface, observability, runbook, and recovery COMPLETED

The public health payload was reduced to a minimal stable response without route/build details. A bounded process-local observability surface records Redis fallback, SSRF blocks, CSRF failures, denied documentation requests, production-guard warnings, broker failures, repeated authentication failures, budget-hold leaks, and migration failures. The operations runbook documents health checks, signal interpretation, production configuration categories, rollback without volume deletion, data-key recovery, and sandbox recovery without restoring a Docker socket or enabling unsafe subprocess fallback.

Cross-phase image-generation remediation COMPLETED

Image generation received reliability and safety work alongside the security phases: model capability/quality routing, image-size/aspect normalization, reference-image authorization and decode limits, response-shape collection and de-duplication, empty-response polling/retry handling with bounded delays, provider fallback behavior, transaction closure before billing settlement, and user-facing feedback for text-only, empty, failed, or retryable provider results. The implementation also addresses polling/deadlock-prone paths by bounding retries, timeouts, cleanup, and reservation settlement. Exact production-provider quality is deployment-dependent and is not claimed by repository tests alone.

6. Findings, deferrals, and residual risk

Closed or materially reduced

  • Unauthenticated/overbroad sandbox execution and direct application socket access.
  • Media object-level authorization gaps and reference-image bypasses.
  • DNS-based SSRF, redirect SSRF, unsafe URL schemes, and proxy-environment surprises.
  • Concurrent budget and API-key credit overrun behavior.
  • Browser JWT persistence exposure, login CSRF/OIDC state weaknesses, and missing session revocation behavior.
  • Production startup with known placeholder credentials or unsafe runtime fallbacks.
  • Excessive public API documentation and health-surface disclosure.
  • Container privilege, filesystem, network, and resource-limit weaknesses.

Deferred or not performed

  • DEFERRED Enforce CSP globally after Report-Only observation and application compatibility review.
  • DEFERRED Replace process-local counters with durable, centralized fleet-wide metrics and security audit records.
  • DEFERRED Complete external penetration testing, independent threat-model sign-off, and production load/abuse testing.
  • DEFERRED Prove every deployment’s secret-manager integration and rotate all non-object-storage credentials.
  • DEFERRED Remove the legacy Bearer JWT compatibility path after all clients migrate to cookie sessions.
  • DEFERRED Validate real-provider image quality and latency across the production model catalog.

Residual risks and explicit limitations

  • Redis outage fallback is fail-open and therefore only approximate across workers; it favors availability over strict abuse prevention.
  • Process-local counters reset on restart and are diagnostic, not billing, compliance, or fleet-wide audit data.
  • SSRF private-range opt-out is powerful and must remain deployment-controlled; unsafe use can reopen the threat.
  • Multi-key decryption preserves compatibility during migration, so the old key remains sensitive until all legacy ciphertext is re-encrypted and the old key is retired.
  • The broker’s Docker socket is still a high-value control-plane capability; isolation reduces exposure but does not make the socket harmless.
  • Repository evidence cannot prove production configuration, backup integrity, external service availability, or user-facing image quality without the manual gates.

7. Final credential rotation scope

Only local S3-compatible object-storage credentials were rotated. No other credentials were changed as part of the final rotation action. This includes application secrets, database credentials, Redis credentials, broker tokens, LDAP/Keycloak credentials, SMTP credentials, provider/API keys, and encryption keys: they are described as categories only and their values are intentionally absent from this report.

Credential rotation is separate from code/configuration remediation. Operators must complete any additional rotation through the approved secret-management process, then run the production guard and health/acceptance checks.

8. Final status and recommended follow-ups

Final status: REMEDIATION IMPLEMENTED IN THE REVIEWED REPOSITORY; PRODUCTION ACCEPTANCE CONDITIONAL. The principal controls and supporting documentation are present. Release sign-off should wait for environment-specific gates and evidence listed below.

  1. Run the full backend/frontend CI test, lint, build, dependency, and image-scan pipelines; archive the actual results.
  2. Perform an isolated backup restore and rollback drill, including data-key migration recovery.
  3. Verify all production services with authenticated Redis, broker health, TLS, HSTS, admin-only OpenAPI, and hard-fail guard settings.
  4. Run an external penetration test focused on SSRF, media authorization, OIDC/session handling, broker abuse, and budget races.
  5. Monitor CSP Report-Only violations, then approve a narrowly scoped enforced CSP.
  6. Deploy centralized metrics and durable audit logging for security signals.
  7. Remove legacy Bearer/browser-token compatibility after client migration and retire old encryption keys after migration evidence.
  8. Revalidate image-provider routing, retries, feedback, cost settlement, and quality with representative production models.
