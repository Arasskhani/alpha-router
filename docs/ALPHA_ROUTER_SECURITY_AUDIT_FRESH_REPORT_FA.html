گزارش تست نفوذ تازهٔ Alpha Router

ارزیابی ایستا و پویا بدون پیش‌فرض قبلی، روی استقرار محلی Docker Compose. این نسخه برای استفاده در شبکهٔ داخلی سازمان بازنویسی شده و شدت ریسک‌ها با همین زمینه تنظیم شده است. هیچ کدی برای remediation تغییر نکرده است.

هدف: alpha، postgres، pgbouncer، redis، seaweedfs، sandbox-broker

۱. خلاصه اجرایی

Alpha Router برای استقرار در شبکه داخلی سازمان ارزیابی شد. بسیاری از کنترل‌ها (کانتینر non-root، احراز هویت Redis، قفل Docs، پیش‌فرض‌های SSRF، توکن broker، مالکیت رسانه/چت برای کاربر عادی) درست کار می‌کنند. ریسک‌های باقی‌مانده بیشتر از جنس افزایش سطح دسترسی داخل سازمان، سوءاستفاده توسط حساب‌های ادمین محدود، و معماری Docker socket هستند — نه لزوماً حملهٔ مستقیم از اینترنت عمومی.

۲. فرض استقرار داخلی و مقیاس ریسک

فرض این گزارش: Alpha Router فقط روی شبکه داخلی سازمان در دسترس است (VLAN/کاربران سازمانی)، نه به‌صورت عمومی روی اینترنت. مهاجم محتمل شامل: کاربر داخلی مخرب، حساب لو‌رفته، بدافزار روی کلاینت سازمانی، یا ادمین با نقش محدود است.

مقیاس شدت در این نسخه:

  • High — امکان تصاحب گسترده، ارتقای نقش حساس، یا کنترل host/Docker از داخل شبکه.
  • Medium — سوءاستفاده عملی با پیش‌شرط حساب/نقش یا پیکربندی غلط؛ اثر محدودتر یا نیازمند چند گام.
  • Low — اثر محدود، یا عمدتاً defense-in-depth روی شبکه داخلی.
  • Very Low — ریسک نظری/عملیاتی جزئی با احتمال یا اثر پایین در زمینهٔ داخلی.

توجه: مواردی مثل bind روی 0.0.0.0 یا نبود HSTS که در اینترنت عمومی «Critical/High» دیده می‌شوند، در شبکه داخلی با فرض فایروال سازمانی معمولاً به Medium یا پایین‌تر کاهش یافته‌اند — مگر اینکه بخش‌های guest/Wi‑Fi ناامن به همان VLAN دسترسی داشته باشند.

۳. محدوده و روش کار

داخل محدوده

  • بررسی ایستای auth، RBAC، gateway، admin، SSRF، sandbox، آپلود/ZIP، OIDC/LDAP، crypto، frontend، Compose، CI
  • آزمون پویا روی localhost (وضعیت HTTP، هدرها، inspect کانتینر، فلگ‌های غیرحساس)
  • راهکار فیکس به‌صورت مشورتی

قوانین سخت

  • بدون تغییر کد، بدون commit، بدون چرخش credential، بدون ویرایش .env
  • بدون exploit سلاح‌شده و بدون حمله به سیستم‌های خارجی سازمان
  • بدون درج مقدار secret در گزارش

۶. شرح یافته‌ها و راهکار فیکس

High · F-15 · ادمین Users می‌تواند Super Admin بسازد

ارتقای سطح دسترسی

چرا در شبکه داخلی High است؟

در سازمان، حساب‌های «مدیر کاربران» رایج‌اند. اگر این نقش بتواند خودش را Super Admin کند، یک insider یا حساب لو‌رفته به کل پنل، اسرار، Docs و تنظیمات هویت دسترسی پیدا می‌کند — بدون نیاز به نفوذ از اینترنت.

محل

backend/app/api/admin.py (PATCH کاربران / نقش‌های گروهی)، user_role_service.py، rbac.py

یافته

به‌روزرسانی نقش فقط به require_users_write وابسته است. حفاظت از حذف آخرین ادمین کامل وجود دارد، اما برای اعطای super_admin (یا مجموعه نقش‌های معادل) گیت جداگانه دیده نشد.

راهکار فیکس
  • اعطای/حذف super_admin فقط توسط Super Admin مجاز باشد.
  • قانون «نمی‌توان نقشی بالاتر از خود اعطا کرد» روی همهٔ endpointهای نقش اعمال شود.
  • تست regression: Users-admin برای ساخت Super Admin باید ۴۰۳ بگیرد.

High · F-01 · docker.sock روی sandbox-broker

SandboxHost

چرا در شبکه داخلی هنوز High است؟

حتی بدون اینترنت، هر کسی که به broker یا توکن آن برسد (از داخل Docker network، از لاگ، از backup) می‌تواند به Docker host مسلط شود. این ریسک معماری است و با «داخلی بودن» حذف نمی‌شود.

شواهد

Inspect: mount شدن sock؛ پورت ۸۰۸۱ publish نشده؛ alpha بدون sock؛ توکن غلط → ۴۰۱؛ USER خالی.

راهکار فیکس
  • Broker را روی host/VM جدا ایزوله کنید؛ توکن را rotate کنید؛ هرگز پورت را publish نکنید.
  • در میان‌مدت: اجرای non-root، یا جایگزینی با runtime بدون sock (gVisor / Firecracker / runner جدا).
  • مانیتورینگ شکست‌های auth broker.

High · F-03 · Legacy Bearer و دور زدن CSRF

چرا در شبکه داخلی High است؟

XSS از یک سایت داخلی دیگر، افزونهٔ مرورگر، یا صفحهٔ مخرب اینترانت می‌تواند JWT لاگین را بدون CSRF مصرف کند. مدل cookie+CSRF عملاً تضعیف می‌شود.

شواهد

زمان اجرا: allow_legacy_bearer_auth=True و enable_csrf=True.

راهکار فیکس
  • پس از soak: ALLOW_LEGACY_BEARER_AUTH=false برای مرورگر.
  • عدم بازگرداندن access_token به SPA؛ نگه‌داشتن API key فقط برای /v1.

High · F-02 · Production Guard در حالت warning

چرا High؟

با ENVIRONMENT=production و warning، پیکربندی ناامن آینده فقط هشدار می‌دهد و سرویس بالا می‌ماند. در سازمان این یعنی drift پیکربندی ممکن است ماه‌ها دیده نشود.

راهکار فیکس
  • پس از چک‌لیست secretها: PRODUCTION_GUARD_MODE=hard-fail.
  • حالت warning فقط برای پنجرهٔ کوتاه مهاجرت.

Medium · F-18 · قدرت بالای ادمین Authentication روی IdP

یافته

ادمین با دسترسی نوشتن Authentication می‌تواند server_url و secretهای IdP را عوض کند. فراخوانی JWKS/token از مسیر SSRF مشترک عبور نمی‌کند. IdP مخرب می‌تواند هویت جعلی وارد Alpha Router کند.

چرا Medium؟

نیاز به نقش خاص دارد؛ ولی اثر در صورت سوءاستفاده بسیار بالا است.

راهکار فیکس
  • نوشتن تنظیمات Keycloak/LDAP را به Super Admin یا dual-control محدود کنید.
  • Allowlist برای hostهای IdP؛ پین کردن issuer؛ عبور از کنترل SSRF.

Medium · F-17 · پین نشدن OIDC redirect_uri

یافته

اعتبارسنجی شکل/HTTPS انجام می‌شود، اما به callback ثابت خود Alpha Router قفل نیست.

راهکار فیکس
  • قفل روی {API_PUBLIC_URL}/api/auth/keycloak/callback یا allowlist صریح.
  • اعتبارسنجی هم در ذخیره و هم در login/callback.

Medium · F-19 · امکان fallback به LDAP plaintext

چرا در اینترانت Medium؟

در شبکه داخلی هنوز sniff/MITM روی VLAN ناامن یا سگمنت مشترک ممکن است. عبور رمز LDAP به‌صورت cleartext برای سازمان حساس است.

راهکار فیکس
  • در production فقط LDAPS یا STARTTLS موفق؛ بدون fallback plaintext.
  • پیش‌فرض trust_untrusted_cert=false و هشدار واضح در UI.

Medium · F-05 · Rate-limit لاگین در قطعی Redis fail-open

Redis الان auth دارد (مثبت). در قطعی Redis، محدودیت لاگین به شمارندهٔ per-worker سقوط می‌کند و brute-force داخلی آسان‌تر می‌شود.

راهکار فیکس
  • برای login به‌صورت fail-closed یا سقف محلی خیلی سخت‌گیرانه.
  • هشدار روی شمارندهٔ redis_fallback.

Medium · F-08 · Fallback decrypt برای plaintext قدیمی

مقادیر غیرFernet به‌صورت plaintext برمی‌گردند؛ ciphertext غیرقابل‌decrypt هم as-is برمی‌گردد.

راهکار فیکس
  • تأیید تکمیل migration؛ پس از cutover رد کردن plaintext در production.
  • برای ciphertext خراب، fail-closed به‌جای برگرداندن بایت خام.

Medium · F-20 · شکاف hold بودجه در تغییر ماه

قفل همزمانی reserve/settle خوب است؛ اما در rollover ماهانه، holdهای باز ممکن است با دورهٔ جدید ناسازگار شوند.

راهکار فیکس
  • قبل از reset دوره: settle/expire کردن holdها، یا انتساب settle به دورهٔ ایجاد reservation.

Medium · F-21 · برگرداندن متن خطای provider

متن خام upstream ممکن است به کاربر یا API لاگ برسد و جزئیات داخلی/کلید را لو دهد.

راهکار فیکس
  • کد خطای پایدار برای کلاینت؛ جزئیات کامل فقط در لاگ سرور.
  • ذخیرهٔ error_code redact‌شده در DB.

Medium · F-10 · broker بدون USER غیرroot

برخلاف alpha، broker معمولاً به‌صورت root داخل کانتینر اجرا می‌شود و همزمان sock دارد.

راهکار فیکس
  • اجرای non-root در صورت امکان؛ محدود کردن دسترسی گروه به docker.sock.

Medium · F-07 · کلیدهای خاموش‌کننده SSRF

پیش‌فرض‌ها امن‌اند. روشن کردن private ranges یا خاموش کردن DNS pinning، سرویس‌های داخلی Docker/سازمان را در تیررس web-fetch قرار می‌دهد — در اینترانت اثرش بیشتر است.

راهکار فیکس
  • قفل کردن فلگ‌ها در production؛ تغییر فقط با تأیید دو نفره؛ هشدار drift.

Medium · F-09 · Private Mode سمت کلاینت

محرمانگی به رفتار مرورگر وابسته است. روی سیستم‌های اشتراکی سازمانی (کیوسک، سیستم همکار) دادهٔ private ممکن است بماند.

راهکار فیکس
  • پاک‌سازی پیش‌فرض در logout؛ هشدار برای دستگاه اشتراکی؛ عدم persist روی کیوسک.

Low · F-04 · Publish اپ روی ۰٫۰٫۰٫۰:۸۰۸۰

چرا از High به Low کاهش یافت؟

در فرض شبکه داخلیِ کنترل‌شده، دسترسی از اینترنت عمومی مطرح نیست. ریسک باقی‌مانده: دسترسی از سگمنت‌های داخلی ناخواسته (مثلاً guest Wi‑Fi مشترک) اگر فایروال host باز باشد.

راهکار فیکس
  • در صورت امکان bind به 127.0.0.1 پشت reverse proxy داخلی، یا محدودسازی با فایروال host به VLANهای مجاز.

Low · F-16 · CORS و localhost با credentials

شواهد: Origin لوکال → ACAO + credentials؛ Origin بد → بدون ACAO. در production داخلی معمولاً کم‌اثرتر است مگر با F-03 ترکیب شود.

راهکار فیکس
  • در production فقط FRONTEND_URL؛ localhost فقط در development.

Low · F-06 · CSP فقط Report-Only

دفاع مرورگر در برابر XSS کامل نیست؛ ولی Markdown بدون raw HTML کمک می‌کند. روی اینترانت اولویت پایین‌تر از RBAC/session است.

راهکار فیکس
  • پس از جمع‌آوری violation، CSP را enforce کنید.

Low · F-22 · نبود rate limit روی Gateway

سوءاستفاده از API key داخلی می‌تواند هزینهٔ مدل را سریع بالا ببرد؛ بودجه تا حدی جلوی آن را می‌گیرد.

راهکار فیکس
  • Rate limit per-key/IP روی Redis؛ سقف سخت‌گیرانه‌تر برای master key.

Low · F-13 · dangerouslySetInnerHTML در ChatCodeBlock

تنها sink شناسایی‌شده از نوع HTML خطرناک؛ وابسته به highlight.js.

راهکار فیکس
  • Enforce CSP؛ پین/بازبینی hljs.

Low · F-25 · مسیر با ../ به SPA می‌افتد

پاسخ ۲۰۰ از نوع HTML اپ است، نه خواندن فایل سیستم. Dist containment جلوی نشت فایل را گرفته است.

راهکار فیکس
  • رد کردن خام مسیرهای دارای .. یا برگرداندن JSON 404 یکنواخت برای escape از /api.

Very Low · F-11 · مقایسه غیر ثابت‌زمانی master key

ریسک timing روی شبکه معمولاً عملی نیست؛ همچنان بهتر است اصلاح شود.

راهکار فیکس
  • استفاده از hmac.compare_digest.

Very Low · F-12 · نمایش ۴ کاراکتر آخر secret ماسک‌شده

فقط برای ادمین دارای دسترسی؛ کمک به تأیید کلید.

راهکار فیکس
  • ماسک بدون decrypt tail؛ فقط طول/اثرانگشت.

Very Low · F-23 · اعتماد HSTS به X-Forwarded-Proto

چرا Very Low؟

HSTS الان خاموش است و استقرار داخلی معمولاً HTTP یا TLS روی proxy داخلی دارد. ریسک عملی فعلی ناچیز است.

راهکار فیکس
  • فقط وقتی TLS سازمانی دارید HSTS را روشن کنید؛ هدر forwarded را فقط از proxy قابل اعتماد بپذیرید.

اطلاعاتی · F-14 · خواندن رسانهٔ دیگران توسط Users-menu

قابلیت عمدی ادمین است، نه IDOR کاربر عادی. نقش Users را با احتیاط بدهید و دسترسی cross-user را لاگ کنید.

اطلاعاتی · F-24 · قدرت LDAP bridge پس از داشتن توکن

بدون توکن fail-closed است و bind پیش‌فرض لوکال است. با توکن معتبر، blast radius بالا است — طراحی پل است، نه باگ fail-open.

راهکار فیکس / بلندمدت
  • پین کردن config سمت سرور؛ rate-limit؛ فایروال؛ چرخش توکن؛ در نهایت LDAPS بومی یا Keycloak Federation.

۷. کنترل‌های موفق

  • alpha_router: non-root، read-only، CapDrop ALL، بدون docker.sock
  • broker: publish نشده؛ الزام توکن؛ سیاست image/network ثابت
  • subprocess ناامن خاموش؛ SSRF private خاموش؛ DNS pinning روشن
  • Gateway بدون کلید → ۴۰۱؛ Origin بد روی login → ۴۰۳؛ Admin بدون auth → ۴۰۱
  • Docs برای ناشناس قفل است؛ Redis نیاز به auth دارد
  • کلیدهای پیش‌فرض ناامن در runtime زنده دیده نشد (CUSTOM/SET)
  • IDOR کلاسیک برای کاربر عادی روی chat/media تأیید نشد
  • Markdown بدون rehype-raw؛ سیاست URL؛ پاک‌سازی کلید JWT از localStorage
  • محدودیت اندازهٔ بدنه و سقف ZIP/نام فایل در مسیرهای بررسی‌شده سالم به نظر می‌رسد

۸. اولویت remediation برای استقرار داخلی

  1. فوری: F-15 (ارتقای نقش)، F-03 (خاموش کردن Legacy Bearer)، F-02 (hard-fail)
  2. کوتاه‌مدت: F-01/F-10 (ایزوله broker)، F-18/F-17/F-19 (هویت سازمانی)
  3. سخت‌سازی عملیاتی: F-05، F-08، F-20، F-21، F-07، F-09
  4. defense-in-depth: F-04، F-16، F-06، F-22، F-13، F-25، سپس Very Lowها

در این مرحله هیچ remediation اعمال نشده است. فیکس فقط پس از تأیید جداگانه انجام شود.

۹. محدودیت‌ها

  • ماتریس کامل دوکاربره CSRF/IDOR در UI به‌صورت end-to-end کامل اجرا نشد؛ مالکیت بیشتر از روی کد و probe بدون auth تأیید شد.
  • LDAP/Keycloak سازمانی واقعی و OpenRouter خارجی مورد حمله قرار نگرفتند.
  • بهره‌برداری عملی از docker.sock فراتر از مستندسازی معماری انجام نشد.
  • ارزیابی شدت برای فرض «فقط شبکه داخلی» است؛ اگر سرویس بعداً اینترنتی شود، شدت F-04/F-06/F-23 باید دوباره بالا ارزیابی شود.
  • هیچ مقدار secret در گزارش نیست.

بیانیه: این سند نتیجهٔ تست نفوذ و تحلیل است. هیچ کد اپلیکیشن برای رفع یافته‌ها تغییر نکرده است.
